# UI content rules

## Principle
Visible text is interface, not filler.

Every string should serve navigation, action, status, information, necessary instruction, constraint, validation, recovery, confirmation or essential context.

## Do not invent
Never fabricate numbers, customer quotes, usernames, business claims, guarantees, security/compliance claims, feature availability or success metrics.

When real copy is missing, prefer an explicit development placeholder over plausible fiction.

## Prefer concise copy
Prefer:
"Balance: $3,420"

over:
"Your current balance
Below you can view the amount currently available in your account."

Prefer:
"Insufficient balance"

over:
"Oops! It looks like you do not currently have enough money available..."

## Headings
Do not add both a heading and paragraph when the heading is already obvious. Do not give every small block its own heading.

## Buttons
Name the action: Save, Retry, Deposit, Remove, Continue.

Avoid vague CTAs such as Get started, Explore, Learn more or Unlock when a specific action exists.

## Errors
Communicate:
1. what failed;
2. what the user can do next, when actionable.

Do not expose implementation details that do not aid recovery.

## Tone
Match the target product. aideia does not impose one universal voice.

## Density
Dense products can use dense copy; minimal products can use minimal copy. Never invent text to make a sparse screen look designed.
